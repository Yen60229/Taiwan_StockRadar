# 跨軌審查修正(完整原文)

> 本文件是三份單軌路線圖完成後,由獨立審查視角產出的 21 條修正意見完整原文,
> 是 [`README.md`](./README.md) 中各 ADR 與補強項目的依據。保留原文以供追溯。

- 【致命矛盾:總工時】三份路線圖各自假設每週 8-12h(後端)、6-10h(前端)、6-10h(雲端),合計 20-32h/週,但前提是 solo 開發者總共只有約 8-12h/週。三份計畫實際上是「三個全職 track 並行」。修正:明訂三軌共用同一個時間池,把總時程拉長 2-2.5 倍,或每個 Phase 明確標示三軌的工時分配比例(例如 Phase 1 = 後端 60% / 雲端 30% / 前端 10%),並砍掉低價值項目(見下)。
- 【缺漏:法律與合規】整份計畫零字提及爬取 TWSE/TPEX/TDCC/HiStock 的法律風險:(1) HiStock 是商業網站,爬取並「再散布」其大戶持股資料(Phase 2 目標『可以給陌生人用』、Phase 4 LINE 推播)有 ToS 與著作權風險;(2) 交易所資訊再利用有授權費議題;(3) 對公眾提供選股/警示服務可能觸及台灣《證券投資信託及顧問法》的投顧行為界線;(4) 收 email 等個資須符合《個資法》(隱私權政策、刪帳號機制)。修正:Phase 1 就加入「資料來源合法性盤點 + 免責聲明 + 隱私政策」任務,並在對外開放註冊前完成,而非只在 Phase 4 回測 UI 放 disclaimer。
- 【缺漏:產品驗證太晚】「找 5-10 個真實使用者」被排在 Phase 4(12-24 月),等於先蓋兩年再問有沒有人要用。修正:移到 Phase 1-2 —— 上線後立即找 3-5 個試用者、加最簡單的匿名使用量統計(哪個功能有人用),用回饋決定 Phase 3-4 要不要做回測/Bot/PWA,並為每個大型功能設「不做的條件」(kill criteria)。
- 【缺漏:對外開放的帳號基本功】後端 Phase 2 目標是「可以給陌生人用」,但整份計畫沒有 email 驗證、忘記密碼/重設流程、刪除帳號。沒有這三樣,真實用戶會被鎖死在門外、垃圾註冊無法擋。修正:排進後端 Phase 2 的 auth 工作,優先序高於 refresh token rotation 的細節打磨。
- 【矛盾:目標架構互相打架(最嚴重的架構矛盾)】後端 Phase 3-4 終態 = ARQ worker + Redis(queue/cache/pub-sub)+ WebSocket 常駐連線;雲端 Phase 4 終態 = Cloud Run min-instances=0 + Cloud Run Jobs,且雲端終態架構圖裡完全沒有 Redis。ARQ 需要常駐 worker 輪詢 Redis,與 scale-to-zero 直接衝突;WebSocket 會把 Cloud Run 實例一直掛著(計費+timeout 問題);Redis 上雲要 Memorystore(~$25+/月)或 Upstash,月費 <$20 的目標立刻破功。修正:先做一份跨三軌的終態架構 ADR —— 若終態是 Cloud Run,就砍掉 ARQ(6 週)與 WebSocket(1 個月),排程直接以 Cloud Run Jobs 為目標、即時通知走 LINE push 即可;若堅持 ARQ+WS,雲端 Phase 4 應改成 Fly.io/常駐 VM 而非 Cloud Run。
- 【矛盾:排程系統在 24 個月內被重寫 4 次】Phase 1 printenv hack → 雲端 Phase 2 換 APScheduler/systemd timer → 後端 Phase 3 換 ARQ cron → 雲端 Phase 4 換 Cloud Run Jobs + Cloud Scheduler。同一個「週末跑 pipeline」需求做了四套。修正:保留 Phase 1 的最小 hack,然後一步到位選定終態方案(建議:host systemd timer 撐到上雲,直接跳 Cloud Run Jobs),刪掉中間兩次重寫。
- 【矛盾:監控堆疊重複建置】後端 Phase 3 要在 VPS 上自架 Prometheus + Grafana;雲端 Phase 2(時間更早)已決定用 Grafana Cloud free tier + Alloy。自架版還會跟 app + Postgres + pandas pipeline 擠同一台 4GB CX22,OOM 風險高。修正:統一採用 Grafana Cloud,刪除後端 Phase 3 的自架 Prometheus/Grafana 任務,只保留 instrumentator 出 /metrics 與自訂業務指標。
- 【矛盾:備份與 Alembic 任務重複列帳】pg_dump + rclone 異地備份同時出現在後端 Phase 3 與雲端 Phase 1-2;Alembic 導入同時出現在後端 Phase 1(12h)與雲端 Phase 1(~1 週);CI 建置同時出現在後端 Phase 1、前端 Phase 1、雲端 Phase 2。工時被重複計算,也可能做出兩套不一致的實作。修正:每個基礎設施項目指定唯一 owner 路線圖,其他兩份只寫「依賴 X」。
- 【矛盾:後端分頁 vs 前端 1,900 列虛擬化】後端 Phase 2 給 /api/screen 加 limit(預設 50、上限 200),前端 Phase 2 卻花 16h 用 TanStack Virtual 虛擬化 1,900 列表格 —— 分頁上線後前端根本拿不到 1,900 列,虛擬化白做;反之若產品體驗要的是「全表一次看+前端排序篩選」,後端分頁就是錯的 API 設計。修正:先做產品決策(全量單頁 vs 伺服器分頁),兩軌只留一個,省下另一邊的工。
- 【順序錯誤:OpenAPI codegen 在 schema 修好之前】前端 Phase 1(Week 5-7)就從 /openapi.json 產生型別,但後端要到 Phase 2 才修 response_model、Decimal 序列化、以及加 /api/v1 前綴 —— 從漂移中的 schema codegen,等 /api/v1 一上前端整包 generated client 作廢重來。修正:把後端「Decimal 改 float 序列化 + response_model 補齊 + 決定 /api/v1」提前為後端 Phase 1 小任務(各約 1-2h),前端 codegen 排在其後;或前端 Phase 1 先只做手動型別修正,codegen 延到 Phase 2。
- 【順序錯誤 + 缺漏:cookie auth 與跨網域部署互相打架】前端 Phase 2 遷移到 httpOnly cookie(SameSite=Lax),雲端 Phase 3 把前端搬去 Cloudflare Pages —— 若前端在 *.pages.dev、API 在自有網域,Lax cookie 跨站不會送出,auth 直接壞掉;Pages 的 PR preview URL 也全數無法登入測試。另外前端寫 access token 進 cookie、後端寫 refresh token 進 cookie,兩份規格不一致。修正:先定 domain 策略(前後端同一 eTLD+1,如 app.example.com + api.example.com),統一 token 存放規格(建議 refresh 走 cookie、access 走記憶體),寫成跨軌 ADR,再動工。
- 【順序錯誤:爬蟲搬上雲之前先驗證 IP 不被擋】TWSE/TPEX/TDCC 對資料中心/海外 IP 有封鎖前例,雲端 Phase 4 把 scraper 搬去 Cloud Run Jobs 前,計畫中沒有任何「從雲端 IP 試爬」的驗證步驟;一旦被擋,可能需要固定 egress IP(Cloud NAT,月費不小)或保留 VPS 專跑爬蟲。修正:雲端 Phase 3 加一個半天的 spike:從 GCP asia-east1 實測全部四個來源可爬,結果決定 Phase 4 的 pipeline 部署位置。
- 【矛盾:資料保留成長 vs Neon 免費層】後端 Phase 2 移除 40% 過濾改存全部候選股完整序列、Phase 4 再 backfill 3-5 年 OHLCV(~240 萬列+索引),雲端 Phase 3 卻假設 Neon Free 0.5GB「夠用一年」。全歷史 + backfill 幾乎必然超過 0.5GB。修正:在 Neon 遷移前實測 pg_database_size,把 Neon Launch($19/月)列入成本估算,或明訂冷資料歸檔策略(如 parquet 到 R2);同時把「月費 <$20」的驗收標準改成含 DB 的真實數字。
- 【缺漏:staging 用 prod 備份還原的個資問題】雲端 Phase 3「staging DB 每週從 prod 備份還原」會把真實用戶 email/密碼 hash 複製到防護較弱的 staging。修正:還原腳本加匿名化步驟(users 表 email 打碼、隨機化 hash)。
- 【時程不實:後端 Phase 1 Week 1-2 的 10 小時】8 個 P0 項目含換 JWT 函式庫(python-jose→PyJWT,牽動所有 auth 路徑)、兩處 race condition 重寫、bcrypt async 包裝、cron 修復 —— 每項都要手動驗證(此時還沒有測試網),10h 明顯低估,實際約 20-25h。修正:排 3-4 週,或把 python-jose 遷移移到 Week 3-6 與第一批 auth 測試同批做(先有測試再換庫,風險低得多)。
- 【時程不實/範疇過大:Phase 4 三軌全擠在第二年】後端 Phase 4(Alert+Bot 3 個月、WS 1 個月、回測 3 個月 = 7 個月)+ 前端 Phase 4(PWA+Web Push+Design System)+ 雲端 Phase 4(Cloud Run 遷移+Terraform 全化,~4 個月)全部落在 12-24 月,以單一時間池計算需要 >40h/週。修正:Phase 4 強制三選一先行(建議:雲遷移 → Alert/LINE → 回測),PWA/Web Push 與 LINE bot 是重複的通知管道,依用戶回饋二選一,另一個刪除。
- 【範疇過大:前端履歷驅動項目應砍或降級】對一個資料源全中文、目標用戶是台股散戶的產品:(1) i18n + en.json(10h)幾乎零用戶價值;(2) Storybook + Chromatic + design system 抽成 workspace package(Phase 3-4 合計 ~22h)對 solo 專案是純開銷;(3) TanStack Router 遷移(12h)—— React Router 現有版本 + URLSearchParams 即可達成「URL 即狀態」。修正:三項全數移到「有真實用戶需求或求職作品集衝刺時再做」的 icebox,省下約 44h 給產品功能或直接降低每週負擔。
- 【缺漏:LINE Messaging API 成本與審核】LINE 免費方案每月推播訊息數有限(目前免費層約 200-500 則/月,依方案),warning:警報引擎一旦有幾十個用戶×每週多則通知就會超量,且 Official Account 需審核。計畫完全沒估這筆錢與申請時程。修正:後端 Phase 4 的 Alert Engine 任務加上「LINE 方案費用試算 + 訊息聚合策略(每人每週一則 digest 而非逐事件推)」。
- 【矛盾:效能驗收標準跨軌不相容】後端 Phase 3 驗收「screen 查詢 p95 <100ms(DB 端)」以本機/同機 Postgres 為前提;雲端 Phase 3(同一時段)把 DB 搬去 Neon ap-southeast-1(~50ms RTT),API 每請求多次 round-trip 後,原驗收標準必然破功;而且 Neon free tier 有 autosuspend,冷啟動首查會到秒級,配上 Cloud Run 冷啟動 = 首次請求數秒。修正:效能驗收標準改成「遷移前/後兩組基準」,並把「合併 4 個 max-date 查詢、減少每請求 round-trip 數」從選項改為 Neon 遷移的前置必要條件。
- 【順序建議:備份演練先於一切上線】雲端 Phase 1 的「手動 restore 驗證一次」是全計畫最重要的一行,但被排在上線任務之後。修正:明訂「第一次成功 restore 演練」為對外開放流量的 gate,順序上先於 DNS 切換。
- 【缺漏:斷捨離機制】兩年計畫沒有任何檢查點問「這個專案還值得投入嗎」。solo side project 最大風險不是技術債而是棄坑。修正:每個 Phase 結尾加一個 30 分鐘的 review 儀式:使用者數/自己使用頻率/剩餘動力三項打分,低於門檻就啟動「維運最小化模式」(只留備份+監控+安全更新),這本身也是成熟工程判斷的展現。
