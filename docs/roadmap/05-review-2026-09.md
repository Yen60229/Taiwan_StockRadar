## B. 藍圖裡的錯誤 / 不完整

1. 🔴 **P0-2 修法不完整**（見上表）。這是資料正確性 bug，修錯地方等於沒修。
2. 🔴 **平台已經不是 Hetzner，且完全沒考慮 ARM**。Phase 1–3 全以 Hetzner CX22 為目標寫；實際上線在 Oracle Ampere A1（aarch64）。影響最大的是 Phase 2「GHCR build → VPS 只 pull」：GitHub Actions 預設 runner 是 x86，要 `docker buildx --platform linux/arm64`（QEMU，慢 3–5 倍）或用 ARM runner，否則 pull 下來的 image 跑不起來。Python 依賴這邊沒問題（pandas / lxml / asyncpg / bcrypt / cryptography 都有 aarch64 wheel，本次 Dockerfile 已據此拿掉 build-essential）。
3. 🔴 **Oracle 規格過時**：`03 §0` 寫 4 OCPU / 24 GB；2026-06 起 Always Free 上限為 2 OCPU / 12 GB（本專案 Stack 已升到此規格）。
4. Phase 1 驗收「api / scheduler 皆 non-root」與「Phase 1 保留 cron-in-container」**互相矛盾**——cron daemon 必須 root。本次改為 image 預設 `USER app`、scheduler 在 compose `user: root`；要全 non-root 得等 ADR-2 Phase 2 換 host systemd timer。
5. `01-backend` Phase 2 仍列「docker-compose 加 redis」「slowapi + Redis backend」，與 ADR-1（cache 用 HTTP header + TanStack Query、rate limit 用 in-memory）衝突，且檔頭「受 ADR 修訂」清單沒列到它。
6. `01-backend` 的目標架構圖還畫著 ARQ / Redis / WebSocket / 自架 Prometheus——四個都已被 ADR-1 / ADR-3 砍掉，圖沒同步。
7. Phase 2 監控「Uptime Kuma 跑在另一台免費機（Oracle free tier）」——現在 Oracle 就是 prod。**搶機用的 E2.1.Micro 跳板 VM 正好拿來當監控機**：不同機器、$0、已經有 SSH 與 msmtp。
8. `scripts/deploy.sh` 的 `REPO_URL` 是 `YOUR_USERNAME/stockradar` placeholder，`--init` 會 clone 錯 repo（✅ 已改）。
9. `docs/deploy-to-vps.md` 驗收用 `/healthz`——這條路徑在 Caddy 後面會落到 nginx 的 SPA fallback，**永遠回 200**，監控上等於瞎的。後端本來只有 `/healthz`，deploy.sh 卻印 `/api/health`（不存在）。（✅ 已加 `GET /api/health`，含 `SELECT 1`，DB 掛回 503；文件改用它）
10. 「偽造 token 觸發 500」措辭過重（見 A 表 P0-5）。
11. **時程**：藍圖 2026-07-07 起算，Phase 1 = 0–3 月；到 09-06 兩個月過去，P0 一項都沒動（時間被 Oracle 搶機吃掉，這不是壞事，但要誠實）。建議 Phase 1 起算日重設為 **2026-09**，Phase gate 日期順延。

## C. 藍圖遺漏

1. 🔴 **Oracle Always Free 的 idle reclaim**。官方政策：連續 7 天 CPU / 網路 / 記憶體使用率 95th percentile 都低於 20% 的 Always Free 實例可能被回收。一台週更、平日幾乎沒流量的機器**正是高風險族群**。解法：把帳戶升級成 Pay-As-You-Go（Always Free 資源仍 $0，但不受 idle reclaim；需綁信用卡），或接受風險並確保每日備份在機器之外。這是 Oracle 比 Hetzner 便宜的真實代價，藍圖只寫了「隨時可能被回收」一句。
2. **手動跑 `run_now.sh` 會寄週報給所有訂閱者**（08-01 的 log：「週報寄送完成：3 位訂閱者」）。每測一次就打擾一次用戶。✅ 已加 `SKIP_EMAIL=1`。
3. **週末污染資料要清理，而且要在 backfill 之後清**。`backfill_history.py`（yfinance）寫的是正確日期；舊 scraper 寫的是週六日期、內容是週五資料 → 兩者並存時同一天被算兩次，20 日均量失真。清理 SQL 見附錄，條件是「週末日期且與前 3 天內某列 close+volume 完全相同」，補班日的真實週六交易不會被誤刪。⏳（Docker 開著才能跑）
4. HiStock 的合規風險藍圖有提，但沒給替代來源。證交所「外資及陸資投資持股統計」（`MI_QFIIS`，每日、每檔、官方）可以直接取代，同時解掉合規與「每週一筆」的粒度問題——已寫進 `00-next-steps.md` Step 2。⏳
5. Windows 上用 Python `write_text` 會把檔案寫成 CRLF（本次審查時親自踩到）；repo 已有 `.gitattributes` 強制 `eol=lf`，這點做對了，但值得在 CONTRIBUTING 或 README 提一句。

## 附錄：週末污染列清理 SQL

```sql
-- ① 先看會刪到什麼（週末日期，且前 3 天內有一列 close+volume 完全相同 = 複製品）
SELECT q.stock_code, q.trade_date, q.close, q.volume
FROM daily_quotes q
JOIN daily_quotes p
  ON p.stock_code = q.stock_code
 AND p.trade_date BETWEEN q.trade_date - 3 AND q.trade_date - 1
 AND p.close = q.close AND p.volume = q.volume
WHERE EXTRACT(DOW FROM q.trade_date) IN (0, 6)
ORDER BY q.trade_date, q.stock_code
LIMIT 50;

-- ② 確認無誤後刪除（同樣條件）
DELETE FROM daily_quotes q
USING daily_quotes p
WHERE EXTRACT(DOW FROM q.trade_date) IN (0, 6)
  AND p.stock_code = q.stock_code
  AND p.trade_date BETWEEN q.trade_date - 3 AND q.trade_date - 1
  AND p.close = q.close AND p.volume = q.volume;

-- ③ 驗收：不應再有週末日期（補班日除外）
SELECT trade_date, COUNT(*) FROM daily_quotes
WHERE EXTRACT(DOW FROM trade_date) IN (0, 6)
GROUP BY trade_date ORDER BY trade_date;
```

> 順序：**先跑 `backfill_history.py`**（寫入正確的週五列）**再跑 ②**，否則週六列是週五資料的唯一副本，刪了就沒了。
